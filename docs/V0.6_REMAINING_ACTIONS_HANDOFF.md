## Action 1 - W2 single-grain v0.6 chunking mode

### Problem

This is not just stale config text. Current production-shaped config still
enables hierarchical behavior:
- `config.example.yaml`: `chunking.router_enabled: true`
- `config.example.yaml`: `chunking.huge_docs.enabled: true`
- `config.example.yaml`: `chunking.huge_docs.levels.fine`
- `src/processing/router.py`: huge docs route to `HierarchicalChunker`
- `src/processing/chunkers/hierarchical.py`: emits `coarse`, `mid`, `fine`
- `src/pipeline.py`: `_chunk_batch()` always calls `attach_parent_ids(...)`

Final v0.6 should not pre-bake navigational hierarchy into Chroma. The retrieval
plane should be:
- Zotero fulltext / normal text: recursive `mid` chunks, 700/100.
- Zotero annotations: `atomic`.
- Obsidian markdown: `mid`, with `heading_path` preserved.
- No `fine`.
- No production dependency on `parent_id`.

`HierarchicalChunker` may remain as legacy/test/experimental code, but it must
not be the v0.6 default path.

### Implementation target

Implement an explicit v0.6 chunking path without deleting legacy machinery.
Use the smallest change that makes the v0.6 default safe.

Recommended design:
1. Add a config knob under `chunking`, for example:
   ```yaml
   mode: v0.6_single_grain  # v0.6_single_grain | legacy_router
   ```
   or equivalent. Keep naming simple and documented.
2. Make `create_chunker()` choose the v0.6 router/path when this mode is set.
3. In v0.6 mode:
   - `zotero_annotation` -> `AtomicChunker`
   - Markdown/Obsidian -> `MarkdownChunker` if needed for `heading_path`, but only `mid`
   - everything else -> recursive `TextChunker` using `chunking.defaults` or
     `chunking.chunk_size`/`chunk_overlap`
   - never call `HierarchicalChunker`
4. Ensure `attach_parent_ids()` is not required in v0.6 mode. Either:
   - do not call it when mode is v0.6, or
   - let it no-op because v0.6 chunks lack `parent_level`/`parent_ordinal`.
   Prefer the explicit no-call so future readers see the architecture decision.
5. Update `config.example.yaml` so the default is v0.6 single-grain. Leave legacy
   router settings documented as legacy/experimental if retained.
6. Update user-facing text that still recommends `coarse`/`fine` as normal v0.6
   usage. Search:
   ```bash
   rg -n "coarse|fine|parent_id|hierarchical|router_enabled|huge_docs" docs src scripts tests
   ```

### Files to inspect/edit

- `config.example.yaml`
- `src/factories/chunker_factory.py`
- `src/processing/router.py`
- `src/processing/chunker.py`
- `src/processing/chunkers/markdown.py`
- `src/processing/chunkers/atomic.py`
- `src/pipeline.py`
- `src/enumeration.py`
- `src/mcp_server.py` and `scripts/query.py` text/help only, if they still
  present coarse/fine as first-class v0.6 options
- tests under `tests/unit/test_router_routing.py`, `tests/test_smoke.py`,
  `tests/unit/test_chunk_id_stability.py`

### Tests to add/update

Add focused tests that build chunks in v0.6 mode:
- Zotero fulltext text -> all chunks have `chunk_level == "mid"`.
- Huge Zotero fulltext no longer produces `coarse` or `fine`.
- Zotero annotation -> exactly `atomic`.
- Obsidian/markdown -> `mid` chunks and `heading_path` preserved where present.
- v0.6 mode produces no `parent_id` metadata.
- Legacy router tests may stay, but must explicitly set legacy mode.

### Acceptance

## Action 2 - W8 survey / aggregate-by-source retrieval mode

### Problem

The current query path returns flat chunk hits. Diversity limiting can reduce
repeat sources, but it does not produce the v0.6 "broad survey" view that
replaces coarse-level survey chunks.

### Implementation target

Create shared core logic that:
1. Runs a normal vector recall over v0.6 `mid` chunks.
2. Groups hits by registry identity:
   - Zotero chunks -> `zotero_key`
   - Obsidian/local chunks -> `source_id`
3. Ranks sources by a transparent formula, initially:
   - best score descending
   - then hit count descending
   - then title/identity for deterministic ordering
4. Pulls source metadata from `SourceRegistry.list_sources_payload()` or a new
   registry helper that can fetch by identities.
5. Returns:
   - identity field/value
   - title, authors, year
   - item_type, doi, abstract, tags, venue, language, collections
   - hit_count
   - best_score
   - representative chunk ids/snippets/scores

Keep this separate from formatting. A likely home is `src/retrieval/survey.py`
or a `ResearchRAGPipeline.survey_sources(...)` method delegating to a helper.

### Files to inspect/edit

- `src/pipeline.py` query flow
- `src/retrieval/diversity.py`
- `src/retrieval/filters.py`
- `src/registry.py`
- `scripts/query.py` or a new CLI command if the existing CLI shape is awkward
- `src/mcp_formatters/formatters.py` for future shared formatting
- `src/mcp_server.py` schema later; MCP runtime tests can wait

### Tests to add/update

Use fake vector search results and a temp registry:
- Multiple chunks from one source aggregate to one source row.
- Source with best score ranks above source with lower best score.
- Hit count breaks ties.
- Registry metadata is included.
- Supports `item_type`, `language`, `tag`, collection-style filters if the
  action chooses to expose filters at this stage.

### Acceptance

## Action 3 - W1 extraction seam, quality gate, and provenance

### Problem

The extraction decision has been researched, but the indexing pipeline still has
PDF extraction logic inline in `src/sources/zotero.py` and `src/extract_text.py`.
There is no operational one-method extractor seam, no quality-gated router in
the indexing path, and no register provenance columns.

### Implementation target

Build the seam first, then wire it to Zotero attachment extraction.

Recommended shape:
1. Create `src/processing/extraction/`.
2. Define dataclasses/interfaces:
   - `ExtractionInput`: file path, attachment key, MIME/content type, source metadata
   - `ExtractionOutput`: text, extractor name, version, quality profile/grade,
     action (`accept`, `clean`, `escalate`, `reject`), warnings/errors
   - `BaseExtractor.extract(input) -> ExtractionOutput`
3. Implement candidates:
   - Zotero fulltext cache/API as the zero-cost first candidate when configured.
   - pdfminer fallback using existing `extract_pdf_text`.
   - Marker escalation as optional/config-gated. Do not make Marker required for
     the basic test suite if dependencies are heavy.
4. Use `src/extraction_quality.py` to score outputs.
5. Apply deterministic cleanup where the quality gate says `clean`.
6. Thread provenance into every fulltext document metadata:
   - `extractor`
   - `extractor_version`
   - `extract_quality`
   - `extract_action`
   - optionally `extract_warnings`
7. Add registry `sources` columns for extraction provenance:
   - `extractor`
   - `extract_quality`
   - optionally `extract_action`
   Store source-level first-good/most-severe values; keep it simple.

## Action 4 - Structured chunk/source failure reporting

### Problem

Long indexing runs need a durable report of what failed and why. This is both
engineering observability and corpus-quality data Colin can use to repair source
data.

### Implementation target

Create a structured run report under `runs/{RUN_ID}/` or the configured output
folder. It should be append-friendly and durable enough for long jobs.

Capture failures and quality warnings at these stages:
- source fetch
- extraction
- extraction quality gate
- cleaning
- chunking
- oversize guard split/truncate/skip
- quality filter drop
- embedding
- storage
- registry write
- ledger write/reconciliation

Each record should include:
- run id / timestamp
- stage
- severity: info/warn/error
- source identity: `zotero_key` or `source_id` when known
- document id
- source type
- attachment/note/annotation key if applicable
- chunk id if applicable
- text length / token estimate when relevant
- extractor/provenance when relevant
- exception class and message when relevant
- remediation category:
  - source_data
  - extraction_quality
  - chunking
  - embedder_limit
  - vector_store
  - registry
  - ledger
  - code_bug

Recommended implementation:
- `src/run_reporting.py` with a `RunReporter` class.
- JSONL for event stream plus optional summary JSON at end.
- Keep report writes best-effort but not silent: console warn if reporter fails.
- Thread a reporter through `ResearchRAGPipeline`, or let the pipeline own it and
  pass callbacks to source/extraction/chunk/embedding stages.

## Action 5 - W5 durable state writes with fsync

### Problem

flush or replace but do not `fsync`, and some write directly.

### Implementation target

Create a shared helper, likely `src/io_utils.py` or `src/durable_write.py`:
```python
def write_json_durable(path: Path, payload: Any, *, indent: int = 2) -> None:
    ...
```

Required semantics:
1. Write to a temp file in the same directory.
2. `json.dump(...)`
3. `flush()`

## Action 6 - W10 ledger parity suite and sidecar retirement gate

### Problem

Ledger execution exists but is intentionally not the default. The sidecar
`zotero_delta_state.json` and `vault_files` compatibility remain until parity is
proven.

### Implementation target

Build a parity suite before retiring anything.

Efficient test strategy:
1. Pure planner parity tests:
   - seed ledger from initial source enumeration
   - mutate fixture DB/vault
   - compare legacy delta parent-grain decisions with `build_work_plan(...)`
2. End-to-end small-corpus parity:
   - run with `indexing.ledger.execute=false`
   - reset empty dev Chroma/registry
   - run with `indexing.ledger.execute=true`
   - compare final registry source/chunk membership and status reports
3. Granularity proof:
   - adding a Zotero note to a parent with a large attachment must not re-embed
     unchanged fulltext in ledger mode
   - metadata-only parent edit must update metadata with zero embedding
4. Crash/resume proof:
   - simulate interruption after Chroma upsert/registry chunk record but before
     `record_unit_states`
   - next ledger run re-plans and converges without duplicate chunk rows

Mutation cases to include:
- add Zotero note
- edit Zotero annotation/comment
- replace attachment content/fingerprint
- metadata-only tag/collection/title edit
- delete Zotero parent
